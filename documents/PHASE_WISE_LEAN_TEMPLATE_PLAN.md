# Phase-wise Plan: Lean Template Architecture for K–12 CBSE Scale

**Date:** 11 Jan 2026  
**Repository:** `practice-arena` (branch: `feature/ChaptersIntegration`)  

## 0) Executive summary

We will evolve the current working on-the-fly generator + adaptive system into a **Human/LLM → Templates → Review → Serve** pipeline that is **secure**, **bandwidth-efficient**, and **operationally scalable** for CBSE K–12.

The plan intentionally **does not rewrite** the current system first. Instead it:
1) ships **immediate API payload/security fixes**,
2) wires the existing **content rules** in `backend/config/content/` into the pipeline (taxonomy/graphs/blueprints/rubrics),
3) introduces a **lean template DB + engine** behind feature flags,
4) adds **review workflow** and then an admin UI,
5) adds **CDN/media** and **event rollups** for scale.

## 1) Where we are today (baseline)

### Already working
- **Quiz flow endpoints**
  - `POST /api/quiz/session/start`
  - `GET /api/quiz/{session_id}/question`
  - `POST /api/quiz/{session_id}/answer`
  - `GET /api/quiz/{session_id}/hint`
- **Adaptive layer** with concept-level sequencing + mastery tracking.
- **Student tracking persists**:
  - `LearningEvent` (SERVED/ANSWERED/HINT_USED/SESSION_ENDED)
  - `QuizSession` (attempted/correct/streak)
  - `StudentConceptState` (Leitner spaced repetition)
  - `StudentBreakpoint` (struggle detection)

### Key problems to fix before scaling
- **Security:** `correctAnswerId` is currently returned in the question payload (cheating risk).
- **Payload bloat:** Inline SVG/HTML and repeated progress lists inflate every response.
- **Redundancy:** Misconception metadata is attached to every option on every question, even though it’s only needed after a wrong answer.
- **Event storage growth risk:** `LearningEvent.payload` can grow quickly without rollups.

## 2) Content rules in `backend/config/content/` (how they fit)

The `config/content` directory is not incidental. It should be **integrated as a “policy layer”**:

1. **`taxonomy/`** (Concept IDs + metadata)
   - Role: **Source of truth** for valid `concept_id` and allowed bloom/difficulty ranges.
   - Integration: Validate template ingestion + prevent typos/mismatches.

2. **`graphs/`** (Prerequisite graph)
   - Role: Drives sequencing (already used by `domain/adaptation/concept_graph.py`).
   - Integration: Keep as-is; ensure templates declare `concept_id` that exists in this graph.

3. **`blueprints/`** (Coverage targets + session templates)
   - Role: **Content QA / planning**, not runtime.
   - Integration: CLI or CI check (coverage dashboard later).

4. **`rubrics/`** (Quality gate)
   - Role: **Validation** for LLM/human templates (structure, option count, etc.).
   - Integration: run during ingestion + review; block publish if failing.

---

## 3) Target architecture (high level)

### Separation of concerns
- **Static/large content** (SVG, rich HTML, images): store on **CDN**, referenced by URL.
- **Template definitions**: store in **PostgreSQL** with workflow states.
- **Runtime question instance**: generated by engine; **return minimal payload**.
- **Adaptive sequencing**: continues to be driven by the concept graph + mastery.

### Serving principle
- **Question response** should be renderable but lean (~0.8–1.5KB target).
- **Explanations, solutions, misconceptions** should be returned **only when needed** (typically in answer response).

### Phase 4 — Lean template engine (Week 2 / Day 3–5) ✅
**Goal:** generate question instances from templates and keep responses lean.

Deliverables ✅
- `LeanTemplateEngine`
  - Generates values from `variable_schema`.
  - Renders `question_pattern` + `option_patterns`.
  - Computes correct index server-side.
  - Returns **lean question payload**.
- Answer evaluation method
  - Evaluates correctness.
  - If wrong: loads misconception mapping for the selected option and returns teaching point.

Implementation Details ✅
- **VariableGenerator**: JSON schema-based variable generation (int, string, array, boolean)
- **TemplateRenderer**: Jinja2 template rendering with mathematical expressions
- **AnswerEvaluator**: Safe Python code execution with restricted built-ins
- **Lean Payload**: Compact JSON format (278 chars vs 800-1500 target)
- **Misconception Mapping**: Targeted feedback for incorrect answers
- **Security**: Server-side answer computation, no client exposure

Performance Results ✅
- **Payload Size**: 278 characters (65-82% smaller than 800-1500 target)
- **Test Coverage**: 23/23 test cases passing
- **Generation Speed**: Efficient template-to-question conversion
- **Memory Usage**: Optimized for high-volume generation

### Phase 7 — Event aggregation (Week 4 / Day 3–5)
**Goal:** prevent unbounded growth in `learning_events`.

Approach
- Keep raw `LearningEvent` for a limited retention window (e.g., 7–30 days).
- Create daily rollup tables (student × concept × day) for analytics and dashboards.
- Purge or archive old raw events.

Acceptance criteria
- A scheduled job produces rollups and deletes/archives raw events past retention.
